Sparse GE vs Dense GE Two implementations of the same Gaussian elimination over GF(2) used to solve a cluster (or the whole residual) inside the PPVH erasure decoder. Same answer, different data structure, different cost. Each idea is refreshed, given a tiny pen‑and‑paper example, then linked to the exact code.

GF(2) linear algebra Gaussian elimination Sparse vs dense Python + NumPy

Both solvers answer one question: given a parity-check matrix H, a syndrome s, and the set of erased columns, find an error e (living only on erased columns) with H·e = s (mod 2). They reduce the system to row echelon form and read off a minimum-weight solution. The only difference is how the matrix is stored and which entries get touched during elimination — dense keeps every 0 and 1 in a full array, sparse keeps only the positions of the 1s.

The 30-second picture
A row of H over GF(2) is just a set of column positions that hold a 1. Adding two rows (the core step of elimination) is XOR: shared 1s cancel. Dense GE represents a row as a full array of 0/1 and XORs whole rows (zeros included). Sparse GE represents a row as the set of its 1-positions and XORs by symmetric difference of those sets — it never stores or visits a zero. With the same column order both produce the identical reduced form and the identical minimum-weight solution; they only differ in memory and speed.

1 · Same problem, same answer

Key idea
Both backends solve H·e = s (mod 2) restricted to the erased columns by computing a reduced row echelon form (RREF) of the augmented matrix [H | s], then setting every free variable to 0 and reading the pivot variables straight off the reduced syndrome column. That “free variables = 0” choice is the minimum-weight particular solution. For a fixed column-visitation order the set of pivot columns and the reduced augmented column are unique, so dense and sparse return exactly the same error vector. The data structure changes the cost, never the result.
Heads-up
“Sparse GE” here means a custom, pure-Python GF(2) elimination over a list-of-sets — there is no scipy.sparse, no external solver. “Dense GE” is the project’s original standard_form Gauss–Jordan over a NumPy array. Both are exact mod-2 arithmetic: no floating point, no rounding.

2 · Dense GE: a full 0/1 array

Key idea
The matrix is a dense m × n NumPy array of 0s and 1s. Non-erased columns are explicitly set to 0, the syndrome is appended as an extra column, and a Gauss–Jordan sweep clears each pivot column from every row at once. A pivot step (a) swaps the pivot row into place, then (b) XORs the pivot row into all other rows that have a 1 in the pivot column — implemented as one big outer-product XOR over the whole right-hand block, zeros and all.
Pen & paper
Three checks over six columns; every entry is physically stored, including the zeros:
c0 c1 c2 c3 c4 c5 | s row0: 1 1 0 0 0 0 | 1 row1: 0 1 1 0 0 0 | 0 row2: 0 0 1 1 0 0 | 1
To clear column c1 below row0 you would XOR row0 into any row holding a 1 in c1, rewriting the entire row array (all six columns plus the syndrome), even the long run of 0s on the right. Cost scales with the full width n, not with how many 1s the row actually has.
In the code
Hypergraph_Product_Code_Construction_v3.py · standard_form(...) The pivot swap and the whole-block XOR are the heart of the dense RREF: 
k = np.argmax(M[i:, j]) + i      # find a pivot (a 1) in column j
...
temp = np.copy(M[k]); M[k] = M[i]; M[i] = temp   # physically SWAP rows
aijn = M[i, j:]                  # pivot row, columns j..n
col  = np.copy(M[:, j]); col[i] = 0   # everyone else with a 1 in column j
flip = np.outer(col, aijn)       # full m x (n-j) block of XOR updates
M[:, j:] = M[:, j:] ^ flip       # entrywise XOR over the whole block
utilities.py · _dense_solve_classical_syndrome_with_erasure(...) The wrapper zeroes the non-erased columns, augments with the syndrome, calls standard_form, and reads off the min-weight solution (free variables left at 0): 
H_zeroed = H.copy()
for bit_index in range(num_bits):
    if (bit_index not in E_index_set):
        H_zeroed[:, bit_index] = 0          # drop non-erased columns
H_aug = np.hstack((H_zeroed, s[:, np.newaxis]))   # augment [H | s]
H_aug_rref, A, pivot_indices = standard_form(H_aug)
# pivot variables take the reduced syndrome value; free variables stay 0

3 · Sparse GE: rows as sets of 1-positions

Key idea
Each row is a Python set containing only the column indices where it has a 1 (the syndrome bit is a sentinel column index). Non-erased columns are simply never inserted — there is nothing to “zero out”. Adding one row to another over GF(2) is the symmetric difference of the two sets (^=): positions present in both cancel, the rest survive. Pivoting does not move data — it just selects the first available row that contains the pivot column. Work scales with the number of 1s, not with m × n.
Pen & paper
The same three rows from §2, now as sets of 1-positions (syndrome 1s become the sentinel column s):
row0 = { c0, c1, s } row1 = { c1, c2 } row2 = { c2, c3, s }
Eliminate c1 from row1 by XOR-ing row0 into it — a symmetric difference:
row1 ^= row0 { c1, c2 } ∆ { c0, c1, s } = { c0, c2, s } (c1 is in both → cancels)
Only the handful of touched indices change; the absent columns (c4, c5) are never even mentioned.
In the code
utilities.py · _sparse_solve_classical_syndrome_with_erasure(...) Build each row as a set of erased-column indices (plus the syndrome sentinel), then eliminate by symmetric difference: 
aug_col = num_bits        # sentinel index that stands for the syndrome column
rows = []
for r in range(num_rows):
    row_set = set()
    for c in erased_cols_set:     # ONLY erased columns are ever inserted
        if H[r][c]:
            row_set.add(int(c))
    if s[r]:
        row_set.add(aug_col)      # a 1 in the syndrome
    rows.append(row_set)

for j in candidate_cols:          # pivot-selection order (natural, or DFS)
    # pick the first still-available row that contains column j  (no row swap)
    pivot_set = rows[pivot_row_index]
    for idx in range(num_rows):
        if (idx != pivot_row_index) and (j in rows[idx]):
            rows[idx] ^= pivot_set    # GF(2) row add == set symmetric difference
The min-weight read-off mirrors the dense path: free variables stay 0, each pivot variable takes the value of the augmented sentinel in its pivot row. A pivot landing on aug_col means a “0 = 1” row — an inconsistent system — exactly as a pivot in the dense augmented column would signal.

4 · One system, both ways (hand trace)

Pen & paper — same input, same output
Solve the §2 / §3 system with natural column order (c0, c1, c2, c3, …).
Dense (whole rows) Sparse (sets of 1s) --------------------- -------------------- [110000|1] {c0,c1,s} [011000|0] {c1,c2} [001100|1] {c2,c3,s} pivot c0 -> row0 (nothing below has c0) pivot c1 -> row0; clear row1: [110000|1] {c0,c1,s} [101000|1] (row1 ^= row0) {c0,c2,s} (row1 = {c1,c2} ∆ {c0,c1,s}) [001100|1] {c2,c3,s} pivot c2 -> row1; clear row2: [001100|1] -> row2 ^= row1 [110000|1] {c0,c1,s} [101000|1] {c0,c2,s} [100100|0] {c0,c3} (row2 = {c2,c3,s} ∆ {c0,c2,s})
Read off with free variables = 0. Both representations give the same pivot columns {c0, c1, c2} and the same reduced syndrome bits, hence the identical solution e. The sparse trace only ever wrote the indices that mattered.
Heads-up
This equality holds for the same column order. Turning on DFS changes the order in which columns are chosen as pivots (sparse and dense alike), which can change which minimum-weight solution is returned when the system is under-determined — but it is still a valid minimum-weight solution with the same syndrome.

6 · Fill-in and why DFS reordering exists

Key idea
Sparsity is not free forever. Every XOR can add new 1-positions to a row (symmetric difference grows when the two sets barely overlap). This is fill-in: a row that began with a few 1s can swell as elimination proceeds, eroding the sparse advantage. Dense GE pays the full width regardless, so it does not “notice” fill-in — but it is always paying the worst case.
Heads-up — this is the motivation for DFS
Because fill-in depends on the order in which columns are eliminated, choosing a good order matters for the sparse solver. The project’s DFS column reordering walks the Tanner graph induced by the erased columns and emits a pivot order that keeps eliminations local, aiming to limit fill-in. DFS changes only the order (and therefore which particular min-weight solution is read off); it does not change the backend or the syndrome. Its cost is measured separately and excluded from “GE time / elimination only”.

7 · Where each is used in this project

In the code
utilities.py · perform_classical_syndrome_analysis_with_erasure(...) There is a single matrix-solve entry point. Both the cascade decoder’s per-cluster solve and the peeling→GE pipeline’s global solve call it; it dispatches on SOLVER_CONFIG["backend"] and times the call (subtracting any DFS reordering): 
if (backend == "sparse"):
    predicted_e = _sparse_solve_classical_syndrome_with_erasure(H, s, E_index_set, reorder=reorder)
else:
    predicted_e = _dense_solve_classical_syndrome_with_erasure(H, s, E_index_set, reorder=reorder)
# a final  H . predicted_e (mod 2) == s  assertion guards both paths
Key idea — which experiments use which
The backend is fixed per experiment condition via set_solver_config: dense / dense_dfs use Dense GE; sparse / sparse_dfs use Sparse GE. The current C_1600 high-erasure campaign (both peeling→GE conditions and the cascade baseline) is entirely backend = "sparse", so every matrix in that report is reduced by Sparse GE; DFS is the only thing that varies between its two peeling→GE curves.
