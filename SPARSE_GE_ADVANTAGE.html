Sparse GE — Outstanding Use Case & Advantages When the custom GF(2) sparse Gaussian elimination beats the dense one, why, and how it cashes in on a DFS‑reordered residual. Each idea is refreshed, given a tiny pen‑and‑paper example, then linked to the exact code and to real numbers from this project.

GF(2) linear algebra Sparse vs dense Fill-in & DFS ordering PPVH erasure decoder

Both backends compute the same RREF and the same minimum-weight solution of H·e = s (mod 2). They differ only in cost. The headline: Sparse GE outperforms Dense GE when the system is large, low-density, has low fill-in, and only a small fraction of its columns are active — which is exactly the regime of LDPC erasure decoding. A DFS reordering of the residual makes that advantage bigger by keeping elimination local.

The 30-second picture
Dense GE stores every 0 and 1 and sweeps the full matrix width on each pivot — cost O(m·n), fast per element (NumPy/C) but it processes everything. Sparse GE stores only the 1-positions and XORs them as set symmetric differences — cost O(nnz), slow per operation (Python) but it does far fewer operations. Sparse wins when the operation-count saving (nnz ≪ m·n) beats Python’s overhead. DFS reorders the pivots so elimination stays local on the Tanner graph, which keeps nnz from growing (low fill-in) and widens the gap.

1 · The two cost models

Key idea
The entire dense-vs-sparse story is two cost formulas. Dense: a pivot clears a column from every row at once via a vectorized outer-product XOR over the whole remaining block — it touches all m·n entries, zeros included. Sparse: a pivot XORs the pivot row (a small set) into only the rows that actually contain that column — it touches roughly nnz entries. So sparse is worthwhile precisely when the matrix is far from full.
In the code
Hypergraph_Product_Code_Construction_v3.py · standard_form(...) — dense 
flip = np.outer(col, aijn)       # full m x (n-j) block
M[:, j:] = M[:, j:] ^ flip       # XOR the WHOLE block, zeros included  -> O(m*n)
utilities.py · _sparse_solve_classical_syndrome_with_erasure(...) — sparse 
for idx in range(num_rows):
    if (idx != pivot_row_index) and (j in rows[idx]):
        rows[idx] ^= pivot_set   # touch only rows holding column j, only their 1s  -> O(nnz)

2 · The outstanding use case

Key idea — where sparse shines
Sparse GE is at its best when all of these hold — and they hold for HGP / LDPC erasure decoding:
  • Large, low-density matrix. LDPC checks have constant low weight (here a (3,4) family), so nnz ≪ m·n. The bigger the code, the bigger the win.
  • Small active fraction. Only the erased columns are ever inserted; dense still sweeps the full width even after zeroing the non-erased columns.
  • Low fill-in. If elimination keeps rows sparse, the O(nnz) advantage survives to the end of the solve.
Pen & paper — the most extreme case: the global Hz solve
In the peeling→GE pipeline the matrix is the entire Hz (num_checks × num_qubits), but only the residual erased columns are active. Suppose a 1600-qubit code with ~700 erased columns at high erasure:
Dense : sweeps all ~checks x 1600 columns (every pivot, zeros included) Sparse : touches only the ~700 erased columns' 1s (handful per row)
Dense pays for the whole width on every pivot; sparse pays only for what is erased. At low erasure the residual is a tiny sliver of a huge matrix — this is where the ratio is most lopsided in sparse’s favor.

4 · When dense still wins

Heads-up — sparse is not always faster
Sparse loses its edge exactly when its assumptions break:
  • Tiny matrices. NumPy’s vectorized C XOR amortizes its overhead; Python set iteration cannot compete on very small clusters.
  • Dense / heavy fill-in systems. As row-sets grow toward full rows, sparse pays Python overhead on nearly every element and loses to the vectorized path.
  • Very high erasure. The residual becomes large and dense-like, eroding the nnz savings (you can see sparse’s per-call time creep up with erasure).

5 · How sparse cashes in on a DFS residual

Key idea
Sparse GE’s cost is governed by fill-in: each XOR (rows[idx] ^= pivot_set) can add new 1-positions to a row, and how much it adds depends on the order in which columns become pivots. DFS walks the Tanner graph of the residual depth-first and emits a pivot order in which consecutive columns are graph-neighbors. Eliminating along that order keeps every XOR confined to a small local cluster of rows, so fill-in — and therefore nnz — stays small.
In the code
utilities.py · dfs_order(...) builds the Tanner subgraph and walks it 
neighbor_cols = set()
for r in col_to_rows[c]:          # checks touching column c
    neighbor_cols |= row_to_cols[r]   # other erased columns sharing those checks
for nc in sorted(neighbor_cols, reverse=True):
    if (nc not in visited_cols):
        stack.append(nc)         # depth-first: go to a neighbor next
utilities.py · _sparse_solve uses that order as the pivot sequence 
col_order = dfs_order(H, erased_cols_set)   # (reorder == "dfs")

Pen & paper — a chain residual
After peeling strips the dangling parts, suppose the residual is a chain c0 — chk — c1 — chk — c2 — chk — c3.
DFS order (c0,c1,c2,c3): each elimination merges only into the ONE neighbouring row -> ~zero fill-in (this is peeling, generalised to GE) Jumpy order (hub first): one pivot links many far-apart rows -> a dense block forms, every later XOR pays for it
Same matrix, same answer — but the DFS order keeps the row-sets tiny, so every ^= the sparse solver performs is cheap.
Key idea — why DFS pairs with the post-peeling residual
Peeling has already removed the degree-1 (dangling) structure, leaving the cyclic 2-core. That core is where naive column order would generate long-range fill-in. DFS orders the core so GE walks it locally, so the sparse representation never blows up — the elimination (“GE time”) shrinks accordingly.

6 · Caveat: it is not free

Heads-up
DFS has its own cost — building the adjacency and walking it — which is measured separately (total_reorder_time) and excluded from the reported “GE time / elimination only”. On systems that are already nearly fill-in-free (low erasure, mostly resolved by peeling) the elimination DFS saves can be smaller than the reordering it adds, so it is a net loss there. DFS pays off when the residual is large and cyclic enough that natural-order elimination would otherwise generate real fill-in — the high-erasure end of the sweep. The honest way to judge it is to compare, across the full erasure range, the GE time saved against the reorder time spent.
